# План архитектурной переработки A1-A8

## Правила этапа

- Рефакторинг не меняет геометрическое поведение и JSON форматы обмена.
- Каждый этап завершается зелёными без графического интерфейса, настольное приложение и Python регрессия тесты.
- Перемещение и изменение поведения не объединяются в одном коммите.
- совместимость заголовки/цели сборки удаляются только после миграции потребителей.
- Производительность полигональный тестовые примеры фиксируется до A1 и сравнивается после
  каждого изменения; допустимо только объяснённое отклонение.

## Предусловие A1

Текущий M6.1 различие должен быть либо завершён и зафиксирован отдельным коммитом,
либо целиком перенесён в отдельный рабочее дерево/ветка. Смешивать его с CMake и
исходный код перемещения запрещено. Каноническую генерацию можно продолжать независимо в
`artifacts/`.

Зафиксировать исходное состояние:

- 38 без графического интерфейса CTest;
- 38 настольное приложение CTest;
- 31 Python pytest;
- решения всех полигональный CLI тестовые примеры;
- детерминированные байты пробного набора данных;
- длительность пяти базовых алгоритмов как диагностическое сравнительное испытание.

## A1. Архитектурная страховка

Сложность: `S`. Обязателен до остальных этапов.

- Добавить локальные `check-headless`, `check-python`, `check-desktop` предустановки или
  сценарии без привязки к пользовательскому пути Qt.
- Добавить зависимость проверка с список разрешений допустимых цель сборки/включение заголовка связи.
- Разделить текущий `AllTests` минимум на тесты решателя и `LegacyApp`, не меняя тестовый код.
- Добавить контракты набор контрактных примеров с валидными и невалидными клеточный/полигональный JSON, который
  прогоняется C++ синтаксический анализатор, Python модуль проверки и JSON схема валидатор.
- Создать GitHub действия Linux без графического интерфейса + Python и Windows MSVC без графического интерфейса.

Готово, когда нарушение ядро → Qt/прикладной слой либо прикладной слой → конкретный решатель
обнаруживается автоматически, а локальные и CI-команды дают одинаковый набор
тестов. Откат — удаление только новых проверочных цели сборки/рабочие процессы.

Статус реализации: подготовлено в ветке `codex/a1-architecture-safety`.
Добавлены стандартный `tools/run_checks.py`, CMake/включение заголовка/импорт список разрешений,
отрицательные самопроверки, четыре изолированные цели сборки тестов C++, общие контракты
набор контрактных примеров и GitHub действия. Локально пройдены 40/40 без графического интерфейса и 41/41 настольное приложение CTest.
Этап отмечается полностью завершённым после успешного локального прогона настольного приложения
и первого успешного CI запуск; до этого ветка не сливается.

## A2. Общие контракты и честный сборка граф

Сложность: `M`. Обязателен до M6.2.

- Создать общий заголовок ядра для целевой функции, статуса, метрик, метаданных и
  результата проверки, а заголовок поиска — для вида, конфигурации и управления
  решателем; убрать зависимость
  полигональный типы от `gridtypes.h`.
- Ввести префикс включения `aipackaging/nesting`; оставить старые заголовки перенаправляющими.
- Создать `AIPackaging_NestingCore` и временный `AIPackaging_Solver` `INTERFACE`
  совместимость цель сборки.
- Создавать унаследованные домен и прикладной слой только для настольного
  приложения либо тестов унаследованного контура.
- Исправить открытые `PUBLIC` и закрытые зависимости по фактическим публичным сигнатурам.

Готово, когда полигональное ядро и интерфейс командной строки конфигурируются в
чистой директории без Qt,
`AIPackaging_Math` и унаследованный прикладной слой; сериализованные решения побайтово эквивалентны.
Откат — переключение совместимость цель сборки на прежний исходный код список.

Статус реализации: подготовлено в ветке `codex/a2-common-contracts`.
`AIPackaging_NestingCore` владеет нейтральными контрактами,
`AIPackaging_SolverImpl` — прежними восемью единицами трансляции, а
`AIPackaging_Solver` сохраняет старые включение заголовка/связь компоновки точки входа. Локально
пройдены чистый раскрой 39/39, полный Windows без графического интерфейса 41/41, MSVC+Qt настольное приложение
42/42 и Python 24/24; Linux/CI считаются непроверенными до публикации ветки.

## A3. Разделение полигонального ядра, JSON и обучения

Сложность: `L`. Обязателен до M6.2.

- Разделить `polygonenvironment.cpp` на нормализация/топология, столкновение и
  зазор, кандидат генерация, целевая функция/растровый и проверка.
- Выделить `AIPackaging_Json`; `nlohmann`/json остаётся закрытый.
- Выделить `AIPackaging_Learning`; он не линкует поиск и Json.
- Разделить привязки pybind11 на общую, клеточную и полигональную единицы трансляции без
  изменения Python API.
- Разделить тесты по новым рабочий цели сборки.

Готово, когда открытый API, действие порядок, целевая функция, исключения и NumPy формы не
изменились; запрещённый зависимость тесты проходят. Откат выполняется цель сборки за
цель сборки благодаря сохранённым перенаправляющий заголовки.

Статус реализации: подготовлено в ветке `codex/a3-solver-modules`.
Вместо одного `SolverImpl` созданы `SearchContracts`, `GridCore`, `PolygonCore`,
поиск, JSON и обучение; цели сборки совместимости сохранены. Полигональная среда и
pybind11 привязки Python/C++ физически разделены по ответственности. Локально пройдены
чистый раскрой 44/44, полный Windows без графического интерфейса 46/46, MSVC+Qt настольное приложение 47/47,
Python 24/24 и эталон семантики для 20 CLI-решений на MinGW/MSVC. Linux/CI
считаются непроверенными до публикации ветки.

## A4. Общий поиск механизм выполнения

Сложность: `M-L`. Желателен до M6.2 и обязателен до добавления новых базовых алгоритмов.

- Выделить общие ограничение времени, отмена, ход выполнения, метрики и метаданные.
- Параметризовать входной порядок, случайные перестановки и жизненный цикл
  лучевого поиска адаптером
  конкретной среды.
- Оставить кандидат перечисление, размещение снизу слева ранжирование, состояние и целевая функция в
  клеточную и полигональную реализации.
- Дать клеточному решателю тот же контракт управления выполнением, не меняя поведения по умолчанию.

Готово, когда размещения и детерминированные счётчики всех тестовые примеры совпадают с
базовых алгоритмов; отмена и ход выполнения проверяются для обоих контуров. Если общий
слой требует ветвлений, специфичных для геометрии, откатить только обобщение алгоритмов,
сохранив общий механизм выполнения счётчиков и отмены.

Статус реализации: подготовлено в ветке `codex/a4-search-runtime`.
`SearchContracts` владеет общими ход выполнения/управление типами, а закрытый механизм выполнения
объединяет порядок, с заданным начальным значением случайный, лучевой поиск, ограничение времени, отмена, метрики и
метаданные. Клеточный и полигональный адаптеры сохраняют выбор кандидатов,
специфичный для домена,
целевая функция и валидацию. Локально пройдены чистый раскрой 44/44, полный Windows
без графического интерфейса 46/46, MSVC+Qt настольное приложение 47/47, Python 24/24 и эталон семантики для 20
CLI-решений; Linux/CI требуют публикации ветки.

## A5. Декомпозиция Python данные конвейер обработки

Статус: завершён в отдельной ветке от A4. Сложность: `M`. Обязателен до
рабочий M6.2 обучение.

- Выделить общие средства канонического JSON, SHA-256, детерминированного gzip и
  ввода-вывода частей набора данных.
- Разделить полигональный формы/рецепты, генерация, кэш, повторное проигрывание и проверка.
- Оформить CLI-команды отдельными обработчики; `__main__` оставляет только синтаксический анализатор и
  диспетчеризация.
- Исключить импорт PyTorch из пути, работающего только с набором данных, и сохранить базовую установку
  без `train` дополнительный набор зависимостей.
- Проверить побайтовый функциональный паритет 1 рабочий процесс/несколько рабочие процессы на замороженный тестовый пример.

Реализованы внутренние `datasets.serialization/cache`, отдельные клеточный и полигональный контуры
генерацию, траектории, конвейер обработки, повторное проигрывание и проверку,
фасады совместимости и CLI
обработчики. Локально Python 30/30, архитектура самопроверки 6/6; A4/A5 минимальные
клеточные и полигональные результаты совпали побайтово. Полное повторное проигрывание проходит через
неизменный C++ пространство действий.

Незавершённый M6.1 не входил в A5. В `M6.1R` его функциональность перенесена поверх
новых границ по компонентам: набор данных v2, возобновление и сравнительное испытание не возвращают
монолитный фасад. Канонический завершение критерий пройден 2026-09-13: 384 задачи и
1920 траекторий полностью проверены, манифест SHA-256 зафиксирован в отчёте
M6.1.
Откат — возврат импортов Python к старым фасадным функциям; форматы обмена не
изменены.

## A6. прикладной слой порты и выполнение адаптер

Сложность: `L`. Обязателен до M6.3 настольное приложение получение вывода модели.

Статус: завершён. Прикладной контроллер выделен в `AIPackaging_Application`,
а файловые, поисковые и потоковые обязанности перенесены в
`AIPackaging_DesktopInfrastructure`.

- Заменить типы решателя в `IPolygonWorkspaceView` на объекты передачи данных прикладного слоя.
- Ввести `IPolygonDocumentGateway`, `INestingJobRunner` и
  `IPolygonWorkspaceOutput`.
- Сделать контроллер однопоточной состояние автомат; перенести `jthread`, признак остановки,
  ограничение частоты и внутренняя реализация вызов в инфраструктура средство запуска.
- Реализовать адаптер базового алгоритма и корень композиции; сохранить поведение M5.
- Подготовить контракт нейросетевой/гибридный внутренняя реализация с обязательным точный валидатор и
  явным детерминированный резервный алгоритм.

Готово, когда прикладной слой тесты работают с имитация порты без решатель, Qt и
файловая система; Qt тесты подтверждают поставленный в очередь доставка, устаревший генерация фильтрация и
отмена семантика. Откат — временный адаптер прежнего контроллер API.

## A7. Полигональный ONNX внутренняя реализация

Сложность: `L`. Выполняется в M6.3 после критерий качества M6.2.

- Реализовать ONNX механизм выполнения адаптер за `INestingJobRunner`/внутренняя реализация порт.
- Проверять метаданные и хеши до запуска.
- Разрешать выбор только действий текущего динамического каталога C++.
- Повторно валидировать результат ядро и сравнивать гибридный через общий компаратор.
- При несовместимой модели или некорректный результат применять явно показанный базовый алгоритм
  резервный алгоритм, не скрывая происхождение.

Готово при функциональный паритет Python/ONNX на проверка, отсутствии невалидных решений и
полном GUI/CLI происхождение. Откат — отключение нейросетевой внутренняя реализация признак признак.

## A8. Вывод унаследованный контур настольное приложение

Сложность: `XL`, но работа дробится по пользовательским сценариям.

- Ввести `BUILD_LEGACY_DESKTOP`, по умолчанию включённый на переходе.
- Запретить новые ссылки из полигональный/прикладной слой модулей на `Board`/`Figure`/события.
- Определить необходимый паритет: импорт/создание деталей, просмотр, запуск,
  ручная корректировка и сохранение либо документированный отказ от части функций.
- Переносить по одному сценарий использования с приёмочный тест.
- После паритета отключить унаследованный контур по умолчанию, затем удалить `Board`/`Figure`,
  универсальные события, старые команды и клеточную Qt-вкладку.
- клеточный исследовательский контур и замороженная воспроизводимость M1-M3 сохраняются независимо от GUI.

Готово, когда ни один поддерживаемый настольное приложение сценарий использования не использует унаследованный контур
цели сборки, старые файлы сцен имеют импортёр либо официально завершённую поддержку,
а чистая сборка настольного приложения проходит без `AIPackaging_Math`, домена и контрактов. До этого
откатом служит признак признак.

## Порядок относительно план разработки

```text
M6.1 checkpoint
  -> A1 -> A2 -> A3 -> A4 -> A5
  -> M6.1R canonical dataset freeze
  -> M6.2 polygon BC/PPO
  -> A6
  -> M6.3 ONNX deployment
  -> A7
  -> A8 по мере достижения polygon desktop parity
```

A1-A5 образуют отдельный архитектурный этап и не должны смешиваться с обучением.
A6 можно проектировать заранее, но рабочий миграция выполняется после
стабилизации ядро/поиск API. A8 не блокирует исследовательский критерий качества.
