## 2. Архитектура и владение

Фактические основные зависимости CMake, без стандартной библиотеки и тестов:

```text
GUI → Application → Editor
DxfImport → Editor
EditorPersistence → Editor + StrictJsonSupport
DesktopInfrastructure → Application + EditorPersistence + DxfImport
                      + Search + Json + PolygonCore [+ OnnxInference]
OnnxInference → Learning + Search + PolygonCore + ONNX Runtime
Learning → GridCore + PolygonCore
Search → SearchContracts + GridCore + PolygonCore
Json → GridCore + PolygonCore + SearchContracts + StrictJsonSupport
StrictJsonSupport → nlohmann_json
PolygonCore → NestingCore + Clipper2
GridCore → NestingCore
CliSupport → Search + Json [+ OnnxInference]
Python binding → Search + Json + Learning
```

`Editor` не включает Qt, файловую систему или типы решателя. `Application`
зависит от `Editor`, а внешние операции выполняет через порты. `DxfImport`
не зависит от Qt и точного ядра. В публичных прикладных контрактах отсутствуют
типы DXF/ONNX/JSON. Отключение ONNX исключает соответствующую цель и
условные ветви. В чистом ядре нет целей приложения, `Editor` и GUI.
Старые файлы библиотек в повторно используемых каталогах сборки не являются
доказательством наличия старых целей: проверялся граф, а не только каталог.

```text
main / корень композиции
  ├─ окно → панели / полотно / диалоги / QSettings
  ├─ PolygonDocumentController
  │    ├─ PolygonEditorSession → неизменяемые редакции + история
  │    ├─ общий ActivePolygonDocument → источник / dirty / valid / running
  │    └─ шлюз + очередь черновиков → атомарная запись и инвалидирование
  ├─ PolygonWorkspaceController → модель / поиск / решение / снимок GUI
  ├─ PolygonImportController → временный сеанс / результат мастера
  └─ PolygonArtifactStore → точные задачи / проверенные решения / модели
       ↑ шлюзы и рабочие потоки удерживают разделяемое владение
```

Результаты фоновых работ удерживаются оболочками RAII до принятия события.
Рабочие средства освобождают `activeJob_` до очереди завершения; функции
обратного вызова контроллеров используют слабое владение и идентификаторы
работ. Диспетчер Qt использует отложенную доставку. Завершение потоков
предшествует уничтожению окна. Эти свойства подтверждены кодом и тестами
отказа очереди, исключения обработчика, уничтожения события и повторного запуска.

Главная архитектурная слабость — состояние документа проецируется вручную
между несколькими владельцами. Формально правильный граф зависимостей не
защитил от R6-01 и R6-03. Граница файлового владения также не выдержана
в одном пути пользовательского сохранения, R6-02.

## 4. Подтверждённые дефекты

Номера строк относятся к исходному коммиту, не к будущим исправлениям.
`S/M/L/XL` — относительная сложность исправления вместе с регрессионными тестами.

### R6-01 — после сохранения под новым именем снимок содержит старый путь

**Дефект, P1, M.** `src/core/app/polygonworkspacecontroller.cpp:433`,
`PolygonWorkspaceController::publish`; потребитель —
`src/gui/polygonmainwindow.cpp:273`, `PolygonMainWindow::saveDocument`.

- Воспроизведение: открыть A, изменить документ, сохранить задачу как B,
  сразу вызвать `Ctrl+S` **без ещё одной редакции**.
- Ожидается: следующий вызов сохраняет B, A остаётся побайтно неизменным.
- Фактически: `ActivePolygonDocument` уже указывает B, но
  `snapshot.document.sourceIdentifier` остаётся A. GUI выбирает A.
  Новая редакторная команда может случайно устранить рассогласование,
  поэтому существенен указанный порядок действий.
- Доказательство: прикладная проба после `saveDocument("new-name.json", false)`
  получила `original.json` в снимке вместо `new-name.json`. Чтение GUI
  подтверждает выбор именно этого поля для следующего сохранения.
- Влияние: непреднамеренная перезапись исходного файла; для бывшего черновика
  возможна запись строгой задачи по прежнему пути черновика.
- Исправление: публиковать источник и путь из одного владельца одновременно;
  не поддерживать независимые изменяемые копии этих сведений.
- Тест: два временных файла, изменение до сохранения как B, затем `Ctrl+S`;
  проверить байты A/B, путь снимка, чистую точку, отмену диалога и отказ записи.
- Связь: дополнение к GUI-04, а не утверждение, что прежний тест GUI-04 не проходил.

### R6-02 — сохранение другого документа удаляет чужой черновик восстановления

**Дефект, P1, M.** `src/core/app/polygondocumentcontroller.cpp:457`,
`PolygonDocumentController::clearRecoveryAfterSave`.

- Воспроизведение: при запуске обнаружить черновик A, не восстанавливать и не
  удалять его; открыть независимую задачу B и сохранить B.
- Ожидается: восстановительный файл A сохраняется, поскольку B им не владеет.
- Фактически: после любого успешного сохранения вызывается
  `removeRecovery(autosavePath_)` без проверки `ownsRecovery_`/идентичности.
- Доказательство: проба `inspectRecovery`, `openProblem("unrelated.json")`,
  `saveDocument` получила `removeCount=1` вместо 0. Реальный шлюз
  `polygon_editable_document_gateway.cpp:554` непосредственно удаляет
  обычный файл по этому пути; он не проверяет принадлежность документу.
- Влияние: потеря единственной восстановительной копии посторонних правок.
- Исправление: согласовать пользовательское сохранение с той же моделью
  владения, которая уже применяется при отмене к чистой точке; явное удаление
  пользователем оставить отдельным сценарием.
- Тест: два документа и реальный временный файл; сравнение байтов/наличия
  чужого черновика, удерживаемая запись, смена документа и отказ удаления.
- Связь: непокрытая ветвь сохранения рядом с GUI-03.

### R6-03 — завершение поиска не возвращает доступность отмены и повтора

**Дефект, P2, S.** `src/core/app/polygonworkspacecontroller.cpp:431`, `publish`.

- Воспроизведение: отредактировать документ, запустить и завершить раскрой.
- Ожидается: `canUndo/canRedo` вновь соответствуют сохранённой истории.
- Фактически: `canUndo = canUndo && !running` необратимо затирает признак
  при первом снимке поиска. Завершение не публикует историю заново.
- Доказательство: проба получила `canUndo=false` после `jobs->complete`,
  хотя перед запуском он был `true` и история не удалялась.
- Влияние: команды интерфейса заблокированы до очередной редакторной публикации.
- Исправление: вычислять доступность из истории и состояния запуска,
  не использовать предыдущий видимый признак как источник истины.
- Тест: завершение, отмена и ошибка поиска при доступной отмене/повторе.

### R6-04 — повреждённая полилиния DXF молча меняет форму

**Дефект, P1, M.** `src/import/dxf/dxf_import.cpp:464`,
`convertLightPolyline`; также непроверенный `parseDouble` у `bulge`, строка 474.

- Вход: закрытая `LWPOLYLINE`, код 90 равен 4, вершины
  `(0,0), (10,0), (broken,10), (0,10)`; единица явно `mm`.
- Ожидается: отказ с номером строки повреждённого числа, без частичной геометрии.
- Фактически: неверный X приводит к `continue`; получаются три сегмента,
  `parsed=1`, `built=1`, диагностик 0, локальных ошибок 0.
  `bulge=broken` также не вызывает ошибки и воспринимается как нулевой изгиб.
- Влияние: исходная деталь заменяется другой допустимой фигурой. Точный
  валидатор проверит уже изменённую фигуру, а не соответствие DXF.
- Исправление: проверять все прочитанные координаты, флаги, число вершин и

## 5. Архитектурный долг

### R6-12 — проекция состояния не имеет единой точки формирования

**Архитектура, P2, M.** `src/core/app/polygonworkspacecontroller.cpp:301`,
`acceptEditableDocument`, `acceptEditedDocument`, `presentEditorHistory`, `publish`;
`src/core/app/polygondocumentcontroller.cpp:135`, `saveDocument`.

Источник, сведения документа и доступность истории заполняются в нескольких
сценариях вручную. Ожидается единая согласованная проекция владельца документа
и сессии. Фактически производные поля одновременно используются как память
состояния; конкретные последствия доказаны R6-01 и R6-03.

Предлагается закрытый построитель согласованного снимка документа/истории и
явные переходы принятия редакции и сохранения. Поиск оставить в отдельном
контроллере, не объединять контроллеры в универсальный класс и не переносить
правила в Qt. Необходим табличный тест переходов

с проверкой пути, редакции, `dirty/valid/running`, актуальности решения и
доступности действий после каждого перехода. Размер файла сам по себе здесь
не является основанием для декомпозиции.

## 6. Риски и пробелы, не объявленные подтверждёнными дефектами

- **Повторяющиеся ключи JSON.** Проба `{"x":1,"x":2}` сохраняет последнее
  значение. Это доказанное поведение общего анализатора, но отдельный запрет
  повторных имён не закреплён в текущем публичном контракте. До изменения
  совместимости требуется решение и общий набор примеров C++/Python.
- **Отмена DXF.** У портов анализа/построения нет токена внутри парсера;
  отмена проверяется вокруг вызова. Закрытие может ждать большой импорт.
  Зависание на конкретном ограниченном входе не воспроизведено; нужны пределы
  размера и управляемые проверки задержки без случайных ожиданий.
- **Отказ итоговой очереди при живом окне.** Ресурс освобождается, но
  контроллер может не получить переход завершения. Отказ при разрушении
  приложения ожидаем; восстановление после отказа при живом получателе
  нуждается в отдельном контракте. Не предлагать синхронную резервную доставку.
- **Исключения при выделении памяти и пользовательской публикации.** Защита
  фоновой границы не доказывает сильную гарантию всех синхронных сценариев.
  Нужны управляемые точки отказа после регистрации артефакта и до принятия
  снимка; обычные тесты ошибок геометрии это не заменяют.
- **Случайные тесты редактора.** `testpolygoneditorcommands.cpp:202`
  действительно выполняет 50×500 действий, но выбирает только изменение
  имени, листа и производственных параметров. Это не случайное исследование
  удаления поддеревьев, связности сегментов и ветвления жестов.
- **ONNX.** Синтетические жадные/случайные эталоны Python и C++ совпали;
  контроль форм читается в коде. Не все варианты повреждённых динамических
  форм, нечисловых внутренних представлений и отказов ORT имеют отдельный
  автоматический пример. Это пробел покрытия, не новая доказанная ошибка.
- **Атомарная запись.** Проверены штатные отказы и сохранение прежнего файла.
  Гонка с внешней заменой назначения/временного имени символической ссылкой
  между проверкой и открытием не моделировалась. Защита от враждебного
  локального процесса не должна подразумеваться без отдельной спецификации.
- **Linux и привязка Python.** `AIPackaging_StrictJsonSupport` — статическая
  библиотека без явно включённого `POSITION_INDEPENDENT_CODE`, в отличие от
  остальных библиотек нативной привязки. На Windows это не мешает сборке;
  возможность включения в общий модуль Linux требует реальной проверки
  компоновщиком. Сбой Linux в R6 не воспроизводился и не объявлен доказанным.

### Расхождения документации и факта

- ADR-0024 описывает отмену как переключение указателя; реализация `undo/redo`
  создаёт копию выбранного документа для восстановления верхней границы
  идентификаторов. История разделяет снимки, но отмена не является только
  переключением указателя. Это не доказательство нарушения лимита памяти.
- Результат памяти в отчёте M8.3 требует корректировки после R6-11.
- Формулировку о строгом импорте нельзя интерпретировать как гарантию
  отклонения любой повреждённой структуры: R6-04–R6-06 показывают исключения.
- Публичные шапки об общем чтении `int64_t` и строгой истории обещают больше,
  чем обеспечено реализацией, R6-07/R6-09. Массовое переписывание комментариев
  не требуется: исправить контракт и код вместе на следующем этапе.
