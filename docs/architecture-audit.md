# Архитектурный аудит A0

Статус: завершён. Дата проверки: 2026-09-11.

## Контекст и границы снимка

Аудит охватывает C++-ядро, Qt настольное приложение, CLI, pybind11, Python/ML, JSON-контракты,
CMake и тесты. В качестве стабильной точки используется коммит `dc68168`
(`feat: integrate polygon solver into desktop`, M5). Отдельно рассмотрен текущий
рабочий каталог с незавершённым M6.1: 13 изменённых отслеживаемых Git файлов, четыре новых
файла и более тысячи строк незакоммиченного различие.

M6.1 не считается частью стабильного базового состояния. Аудит не изменяет рабочий код
и не предлагает начинать реорганизацию поверх смешанного рабочего дерева.

Проверки текущего рабочего дерева:

| Контур | Результат |
|---|---:|
| Windows без графического интерфейса CTest | 38/38, 106,81 с |
| Windows MSVC + Qt CTest | 38/38, 89,63 с |
| Python 3.13 pytest | 31/31, 56,53 с |

Система функционально стабильна. Найденные проблемы относятся прежде всего к
стоимости следующих изменений, а не к текущей корректности результатов.

## Сильные стороны, которые необходимо сохранить

- Полигональная геометрия и валидатор не зависят от Qt и Python.
- Любое решение повторно проверяется детерминированным C++-валидатором.
- Форматы задача, решение, траектория и набор данных версионированы.
- базовые алгоритмы используют начальное значение генератора, ограниченные бюджеты и общий порядок сравнения.
- Кривые переводятся в авторитетную целочисленную геометрию до поиска.
- Python не получает возможности напрямую изменять C++-состояние среды.
- без графического интерфейса, настольное приложение и Python-контуры имеют работающие локальные тесты.

## Фактическая карта компонентов

Объём собственных исходников на момент аудита:

| Область | Файлы | Строки | Наблюдаемая ответственность |
|---|---:|---:|---|
| `src/core/contract` | 20 | 485 | события унаследованного пользовательского интерфейса и интерфейсы представления |
| `src/core/domain` | 26 | 1 496 | унаследованный контур клеточные `Board`/`Figure` |
| `src/core/app` | 58 | 3 834 | унаследованный контур команды и полигональный рабочий процесс |
| `src/solver` | 18 | 4 609 | клеточный, полигональный, ввод-вывод, поиск и обучение |
| `src/gui` | 16 | 1 808 | Qt унаследованный контур и полигональный представление |
| `src/cli` | 1 | 248 | клеточное и полигональное решение задач и проверка |
| `src/python` | 1 | 474 | все pybind11 привязки Python/C++ |
| `python/aipackaging_ml` | 18 | 3 309 | данные, обучение, политика и экспорт |

Фактический граф CMake:

```text
Qt GUI -------> App -------> Domain -> Contract -> AIPackaging_Math
  |              |
  |              +-------> Solver <-------- CLI
  +----------------------> Solver <----- pybind11
```

Стрелка `A -> B` означает «потребитель A зависит от компонента B».
`AIPackaging_App` публично экспортирует домен, контракты и решатель, а GUI публично
экспортирует прикладной слой, контракты, `Math` и Qt. Конфигурация без графического интерфейса отключает только GUI:
домен, контракты и прикладной слой всё равно добавляются безусловно в `src/CMakeLists.txt`.

Внутри `AIPackaging_Solver` границы существуют только по именам файлов:

```text
grid types/environment/search/io/learning
polygon types/environment/search/io/learning
```

Все восемь единиц трансляции входят в одну цель сборки с одной плоской публичной
каталогом включаемых заголовков. Clipper2 и nlohmann/json являются закрытыми
зависимостями компоновки,
что правильно, но их потребители невозможно собирать и тестировать раздельно.

таблица приведена в [целевой архитектуре](target-architecture.md).

## Основные потоки данных и владельцы

### Клеточный исследовательский контур

```text
grid JSON -> gridio -> GridProblem -> GridEnvironment
                                  -> GridSolver -> GridSolutionValidator
                                  -> GridLearningEnvironment -> pybind11 -> Python
```

`GridEnvironment` владеет проверенной задачей и ориентациями. `GridState` является
состояние значений. Обучаемая среда дополнительно владеет состоянием эпизода и
постоянным каталогом действий. Этот контур не подключён к настольное приложение и нужен для
воспроизводимости M1-M3.

### Полигональный исследовательский контур и настольное приложение

```text
polygon JSON -> polygonio -> PolygonProblem -> PolygonEnvironment
                                            -> PolygonSolver -> validator
                                            -> PolygonLearningEnvironment -> Python
                                            -> PolygonWorkspaceController -> Qt
```

`PolygonEnvironment` одновременно нормализует аналитические пути, создаёт
ориентации, проверяет действия, генерирует кандидатов, вычисляет целевая функция,
растрирует признаки и содержит функции независимой проверки. Контроллер
настольного приложения владеет задачей, средой, решением, рабочим потоком и
преобразованием в модель представления.

### унаследованный контур настольное приложение

```text
QtView -> Event -> MainController -> state/commands -> PackingController
                                                -> Board <-> Figure
```

Этот контур использует другую геометрию, другую сериализацию, другую валидацию и
другие правила перемещения. Он не может быть основой полигонального продукта без
повторной реализации уже существующего контракта решателя.

## Реестр проблем

Шкала приоритета отражает риск для развития проекта: `high` требуется устранить
до указанного этапа, `medium` допускает контролируемое откладывание, `low` не
оправдывает самостоятельный рефакторинг. Сложность: `S` — локально, `M` — один
модуль, `L` — несколько границ, `XL` — продуктовая миграция.

| идентификатор | Приоритет | Сложность | Проблема | Срок |
|---|---|---:|---|---|
| A0-01 | высокий | L | решатель является монолитным цель сборки | до M6.2 |
| A0-02 | высокий | M | Общие типы решателя принадлежат клеточному API | до M6.2 |
| A0-03 | высокий | M | прикладной слой и GUI раскрывают API конкретного решателя | до M6.3 |
| A0-04 | высокий | M | Сборки без графического интерфейса и для Python включают унаследованные слои настольного приложения | до M6.2 |
| A0-05 | высокий | M | Нет автоматического контроля архитектурных границ и CI | до M6.2 |
| A0-06 | средний | L | клеточный и полигональный контуры дублируют механизм выполнения поиска | до расширения базовых алгоритмов |
| A0-07 | средний | M | JSON схема не является исполняемым источником истины | до нового формат обмена v2 |
| A0-08 | средний | M | Концентрация обязанностей в крупных файлах | вместе с A0-01 |
| A0-09 | средний | M | Поток выполнения находится внутри контроллер | до ONNX внутренняя реализация |
| A0-10 | средний | L | унаследованный контур владеет объектами и событиями через `shared_ptr`/RTTI | изолировать, затем удалить |
| A0-11 | средний | M | Одна цель сборки тестов C++ скрывает реальные зависимости | вместе с A0-01 |
| A0-12 | средний | S | M6.1 не имеет отдельной стабильной точки | до любого рефакторинга |
| A0-13 | низкий | L | унаследованный контур использует глобальный пространство имён и плоские включения заголовков | не исправлять отдельно |

### Состояние после страховки A1

Ветка `codex/a1-architecture-safety` закрывает отсутствие автоматической
диагностики из A0-05 и разделяет единый тест исполняемый файл из A0-11 без изменения
рабочего кода. Текущие нарушения «прикладной слой/GUI → решатель» не объявлены нормой: они
зафиксированы точечными исключениями с `removeBy: A6`. Монолит решатель, владельцы
общих типов и другие замечания A0 остаются задачами A2–A8.

Критических дефектов, требующих аварийной остановки разработки, не найдено.

### A0-01. Монолитный `AIPackaging_Solver`

Доказательство: `src/solver/CMakeLists.txt` включает клеточную и полигональную среды,
поиск, ввод-вывод и обучение в одной цели сборки. `polygonenvironment.cpp` содержит 868 строк:
аппроксимацию кривых, топология, ориентация, столкновение, кандидаты, растровый,
целевая функция и валидатор. Любое изменение геометрии пересобирает и затрагивает
адаптеры данных и обучения.

Последствие: M6.2 не имеет устойчивой границы между геометрией, поиском и
наблюдение; будущая внутренняя реализация ONNX рискует зависеть от лишнего кода
ввода-вывода и обучения.

Решение: разделить цель сборки на ядро, поиск, обучение и Json, сохранив текущие
публичные функции через временный совместимость цель сборки.

### A0-02. Полигональный контракт зависит от клеточного

Доказательство: `polygontypes.h:9` включает `gridtypes.h`, а `PolygonProblem`
использует `GridObjectiveDefinition`; `PolygonSolution` использует объявленные
там `SolveStatus`, `SolverMetrics` и `SolverMetadata`.

Последствие: клеточный нельзя архивировать независимо, а нейтральные типы имеют
ложного владельца. Изменение клеточный формат обмена контракты способно затронуть полигональный ABI.

Решение: выделить `ObjectiveDefinition`, `SolveStatus`, `SolverMetrics`,
`SolverMetadata` и `ValidationResult` в общие контракты, а общие параметры и
управление поиском — в поиск контракты.

### A0-03. Утечка API решателя в прикладной слой и представление

Доказательство: `polygonworkspaceview.h` включает `gridtypes.h`,
`polygonsolver.h` и `polygontypes.h`; GUI принимает `SolverConfig`, а снимок
содержит `PolygonSolverProgress`, `PolygonObjectiveComponents` и `SolverMetrics`.
`PolygonWorkspaceController` хранит конкретный `PolygonEnvironment`.

Последствие: добавление ONNX или гибридной внутренней реализации либо изменение API решателя требует
пересборки и правок прикладного слоя и Qt. Заявленная граница «GUI получает только
представление модель» соблюдается частично.

Решение: в прикладном слое определить собственные `NestingRunRequest`,
`NestingProgress`, `NestingResultSummary` и `PolygonSceneView`; преобразование к
типам решателя выполнять в инфраструктурном адаптере.

### A0-04. Сборочные флаги не изолируют продуктовые контуры

Доказательство: `src/CMakeLists.txt:2-5` безусловно добавляет домен, контракты,
прикладным слоем и решателем. `AIPackaging_App` публично связывает все три зависимости, а его
включение заголовка пути экспортируют внутренние `services/packing` и `services/io`.

Последствие: интерфейс командной строки только для решателя и пакет Python
зависят от конфигурации унаследованного кода;
нарушения границ маскируются транзитивными включения заголовков и библиотеки.

Решение: собирать ядро/поиск/Json независимо; унаследованный контур прикладной слой/домен создавать только
для настольное приложение или унаследованный контур тесты; заменить широкие `PUBLIC` связи на закрытый там, где
тип не встречается в публичном заголовке.

### A0-05. Границы не проверяются автоматически

Доказательство: репозиторий GitHub не содержит CI. Нет теста запрещённых включение заголовка
или связь компоновки связи. Успех зависит от локальных Windows-команд и установленного Qt.

Последствие: циклическая зависимость или случайный Qt/Python включение заголовка в ядре будет
обнаружен поздно. Воспроизводимый набор данных не защищён обязательной проверкой кода.

Решение: добавить CMake зависимость тесты и GitHub действия для Linux без графического интерфейса,
Python и Windows MSVC; настольное приложение Qt задание сделать отдельным после определения способа
установки Qt в средство запуска.

### A0-06. Дублирование поиск координация

Доказательство: `gridsolver.cpp` и `polygonsolver.cpp` отдельно реализуют ограничение времени,
метрики, порядок, случайные перестановки, усечение лучевого поиска, метаданные и сравнение
частичное решение/полное решение. Геометрическая часть различается, жизненный цикл поиска — нет.

Последствие: отмена и ход выполнения добавлены только в полигональный путь; исправления
бюджетов и статусов приходится синхронизировать вручную.

Решение: общий внутренний `SearchRuntime` и параметризованные алгоритмические
циклы. Ранжирование кандидатов и оценка состояния остаются специфичными для геометрии.

### A0-07. Три реализации контракта данных

Доказательство: JSON схема хранится в `schemas/`, C++ вручную перечисляет поля в
`gridio.cpp` и `polygonio.cpp`, Python отдельно реализует `_require_keys`, хеши,
канонический JSON и проверку манифеста. Механизм выполнения не зависит от схемы JSON.

Последствие: схема, C++ синтаксический анализатор и Python модуль проверки могут расходиться при следующей
версии. Существующие тесты проверяют примеры, но не полную функциональный паритет матрицу.

Решение: синтаксический анализатор формата обмена остаётся ручным и
типобезопасным, но канонические примеры схемы
генерируются один раз и прогоняются одинаково через C++ и Python. Общие Python
канонический/хеш/gzip примитивы должны иметь одного владельца.

### A0-08. Файлы с несколькими причинами для изменения

Доказательство: `polygonenvironment.cpp` — 868 строк,
`polygon_dataset.py` — 896, `packingcontroller.cpp` — 551, `qtview.cpp` — 534,
`polygonio.cpp` — 530, `bindings.cpp` — 510. `polygon_dataset.py` одновременно
описывает формы, генерация, семейство хеширование, кэш, части набора данных, повторное проигрывание и проверка.

Последствие: ревью и локальные тесты сложнее, конфликты между следующими этапами
вероятнее. Сам размер не является дефектом; проблема подтверждается количеством
независимых обязанностей.

Решение: декомпозировать по уже выбранным границам, не вводя библиотеку на каждый
файл.

### A0-09. контроллер совмещает сценарий использования и выполнение инфраструктура

Доказательство: `PolygonWorkspaceController` владеет `std::jthread`, признак остановки,
ограничение частоты ход выполнения, `runId`, UI диспетчеризация, сохранение состояния, проверка и представление
преобразование.

Последствие: второй внутренняя реализация увеличит ветвление контроллер; поток политика сложно
переиспользовать в CLI и тестировать независимо от представление функция обратного вызова очередь.

Решение: контроллер оставить синхронной состояние автомат, а выполнение передать
`INestingJobRunner`. средство запуска владеет потоком, отменой и ограничение частоты; контроллер
принимает типизированные ход выполнения/завершение события с генерация идентификатор.

### A0-10. унаследованный контур время жизни и событие диспетчеризация неочевидны

Доказательство: `Board::add` сохраняет `Figure` и передаёт фигуре
`shared_from_this()` как слушатель (`board.cpp:41-48`); `Figure` хранит слушатели
как `shared_ptr` (`algs.h:50-62`). Аналогично `QtView` сильно хранит `EventListener`,
а `MainController` хранит представление. `Event` производные классы разбираются оператор выбора +
`static_cast`, а отдельные команды — через `dynamic_cast`.

Последствие: `Board`/`Figure` образуют цикл владения до явного `remove`, время жизни
опирается на порядок разрушения, расширение событий не проверяется типами.

Решение: не переписывать этот механизм как самостоятельную инвестицию. Поместить
унаследованный контур цели сборки за флаг, запретить новые зависимости и удалить после достижения
полигональным рабочая область необходимого функционального паритета.

### A0-11. Тестовый цель сборки скрывает модульность

Доказательство: `tests/CMakeLists.txt` собирает домен, прикладной слой, решатель, математический модуль и GUI
тесты в один `AIPackaging_Tests`, который публично линкует почти все библиотеки.

Последствие: тест может использовать транзитивно доступный внутренний API;
изолированная собираемость ядро или Json не проверяется.

Решение: разделить тестовые исполняемые файлы по рабочий цели сборки и оставить CLI
сквозной отдельным уровнем.

### A0-12. Незавершённый M6.1 пересекает критические границы

Доказательство: текущее рабочее дерево изменяет версию, документацию, CLI Python, привязки Python/C++,
набор данных/модуль проверки и схемы; каноническая генерация остановлена до манифест хеш.

Последствие: механическое перемещение файлов смешает функциональный M6.1 различие с
