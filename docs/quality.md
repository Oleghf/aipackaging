# Качество и оценка

## Язык документации

Документация, программные комментарии и человекочитаемые сообщения должны
соответствовать [терминологии проекта](terminology.md). Быстрая проверка
запускается командой `python tools/run_checks.py language`. Новый английский
термин допускается только после русского объяснения и внесения в машинный
глоссарий; точные машинные идентификаторы оформляются как код.

## Сначала корректность

Раскладка допустима только при выполнении ограничений границ, пересечений,
зазора, преобразований и количества. Невалидная раскладка считается ошибкой и
не получает конкурентную оценку использования материала.

## базовые алгоритмы

Минимальный набор:

- `input-first-fit` в стабильном входном порядке;
- `area-left-bottom` и `max-side-left-bottom`;
- `random-left-bottom` с фиксированным начальное значение генератора и числом перестановок;
- ограниченный `beam` по тому же набору кандидатов.

Базовый алгоритм и модель используют одинаковые кандидаты, валидатор, ограничение времени и расчёт
целевой функции.

## Метрики

- доля валидных и полных решений;
- значение выбранной функции ценности остатка;
- площадь и размеры крупнейшего повторно используемого остатка;
- длина занятой полосы от выбранного края листа;
- фрагментация свободной области;
- использование материала как диагностическая, но не единственная метрика;
- занятая ширина/длина или оболочка;
- фактическое время выполнения и число проверенных кандидатов;
- время получения вывода модели отдельно от время геометрических вычислений;
- разрыв с лучшим известным решением или базовым алгоритмом;
- результаты по числу деталей и сложности контуров.

Бизнес-цель и порядок сравнения зафиксированы в ADR-0002. Основная метрика —
`usedLength`; ширина главного остатка равна `sheetWidth - usedLength`. Она должна
одинаково вычисляться для базового алгоритма, оценки модели и UI. Вознаграждение обучения может
иметь дополнительные нормализованные компоненты, но не должен менять порядок
оценки итоговых решений.

В M2 вознаграждение задаётся дельтой смешанный позиционный ранг из ADR-0004. модульные тесты проверяют
его точное целочисленное значение и приоритеты до нормализации. Модуль проверки набора данных
повторно проигрывает каждое действие, сверяет вознаграждение, дублирующее размещение и
итоговое решение независимым C++-валидатором.

В клеточном M1 `largestExtraRectangleArea` вычисляется только левее основной
правой полосы. `fragmentationPenalty` равен числу свободных клеток этой области,
не входящих в её крупнейшую 4-связную компоненту. Формула не содержит
производственных порогов, пока не определены реальные единицы и материалы.

В полигональном M4 допустимость, `usedLength`, ширина правой полосы и площадь
материала вычисляются по микронным кольцам. `largestExtraRectangleArea` и
`fragmentationPenalty` являются воспроизводимыми оценками сетки 128×128 и не
могут изменить приоритет точного `usedLength`. Тесты отдельно покрывают
касание, положительный зазор, вогнутость, отверстия и аппроксимацию кривых.

В M6.2 вознаграждение v2 является дельтой потенциала с компонентами полноты,
площади, занятой длины, дополнительного прямоугольника и фрагментации. Оно не
заменяет точный порядок сравнения. Этап принимается только при 64 полных
гибридных решениях без проигрышей `random-left-bottom/64`, не менее шести
строгих побед и хотя бы одном уменьшении `usedLength`.

Каноническая оценка M6.2 прошла этот критерий: 64 полных тестовых решения,
14 побед, 50 равенств, 0 поражений и 8 уменьшений `usedLength`. Подробные
метрики и хеши приведены в
[отчёте эксперимента](experiments/m6-2-polygon-policy-2026-09-16.md).

Интеграция M5 с настольным приложением дополнительно проверяет отсутствие
изменений `QWidget` из рабочего потока, совместную отмену, игнорирование
запоздалых уведомлений о ходе выполнения,
повторную валидацию перед публикацией и сохранение прежней сцены при ошибке
загрузки или внутренней реализации.

## Протокол данных

- В Git хранятся генераторы и малые распространяемые тестовые примеры, но не наборы данных.
- Версионируются схемы, генераторы, начальное значение генератора и предварительная обработка.
- Разделение выполняется по семействам форм или исходным заказам.
- тестовая выборка не используется при обучении и подборе гиперпараметров.
- Фиксируются происхождение данных и права.
- JSON кодируется канонически, gzip использует `mtime=0`, части набора данных защищены
  SHA-256, а результат не зависит от числа рабочих процессов.
- Нужны сложные случаи: тонкие элементы, почти касающиеся границы, вогнутость,
  повторы, симметрия, отверстия и экстремальные масштабы.

Рабочий полигональный набор данных v2 дополнительно проверяет заявленный профиль сложности, парные
масштабные варианты, отсутствие утечки семейств между выборками, покрытие семи классов,
полное повторное проигрывание пяти базовых алгоритмов и повторный выбор
экспертного результата общим компаратором C++.
Поля фактического времени решений обнуляются. Кэш возобновления используется
только при точном
совпадении идентификатора и отпечатка; сравнительное испытание читает
замороженные траектории и по умолчанию не использует тестовую выборку.

## Уровни тестирования

Модульные тесты покрывают нормализацию, смещения, преобразования, пересечения,
кандидаты, метрики и сериализацию. Тесты свойств проверяют сериализацию с
обратным чтением, симметрию пересечений и инварианты сгенерированных случаев.
Эталонные тесты фиксируют
малые задачи и ожидаемые метрики.

Оценка модели проверяет совместимость схем, воспроизводимое получение вывода
модели с заданным начальным значением, соблюдение маски действий, резервный
алгоритм и точную повторную проверку. Каждый отчёт эксперимента
содержит ревизию кода, версии данных и среды, конфигурацию, начальное значение
генератора, оборудование,
время обучения, бюджет оценки и результаты для каждого экземпляра.

Для M3 контрольная точка выбирается только по проверочной выборке. После этого тестовая выборка из 64
малых и 64 средних задач оценивается один раз. Публикуются пять замороженных M1
базовые алгоритмы, жадный нейросетевой режим, нейросетевой режим с выбором
лучшего из 16 запусков и гибридный режим. Исследовательский критерий требует 128
полных валидных гибридных решений, отсутствие проигрышей `random-left-bottom/64`,
не менее шести строгих лексикографических выигрышей и хотя бы одно уменьшение
`usedLength`. фактическое время публикуется диагностически и не заменяет критерий качества.

## Архитектурная страховка A1

Единая точка запуска локальных проверок не устанавливает зависимости и не
удаляет существующие каталоги сборки:

```powershell
python tools/run_checks.py architecture
python tools/run_checks.py nesting
python tools/run_checks.py headless
python tools/run_checks.py python
python tools/run_checks.py desktop --qt-dir "<путь-к-Qt6Config>"
python tools/run_checks.py all --qt-dir "<путь-к-Qt6Config>"
```

Проверка `architecture` сопоставляет C++ включение заголовка и Python импорты с
`tools/architecture/architecture-rules.json`, включая явных владельцев канонический
и заголовки совместимости, проверяет граф рабочих целей сборки в CMake и
проигрывает отрицательные самопроверки. Самопроверки отклоняют ядро → Qt, обучение → JSON,
`GridCore` → Clipper2, `PolygonCore` → `nlohmann`/json и неизвестные цель сборки связи.
Исключения «прикладной слой/GUI → решатель» удалены в A6. Проверка запрещает
`Application → Search/Json/Qt/PolygonCore`, `App → Solver` и `GUI → Solver`.

C++ регрессия набор тестов разделён на `GridCore`, `PolygonCore`, поиск, Json, обучение,
совместимость, прикладной слой, унаследованный контур и gui исполняемые файлы. CLI-сценарии имеют метки `cli;grid`
и `cli;polygon`. Общий набор контрактных примеров из `tests/contracts/manifest.json` проверяется
строгий C++ синтаксические анализаторы/валидаторы, Python привязка Python/C++ и JSON схема Draft 2020-12.
После A3 ожидаются 44 чистый раскрой, 46 полное решение без графического интерфейса и 47 настольное приложение CTest записи.

После A4 эти итоговые значения не меняются. `AIPackaging_SearchTests` дополнительно
проверяет общий механизм выполнения с внедрёнными монотонными часами, приоритет отмены,
ход выполнения всех пяти базовых алгоритмов, возврат валидного частичного решения и отсутствие влияния
пассивного функция обратного вызова на размещения, целевая функция и детерминированные счётчики.
Эталон семантики по-прежнему сравнивает 20 решений CLI с базовыми алгоритмами
A1/A3. Локально
пройдены: чистый контур раскроя 44/44, полный контур без графического интерфейса
46/46, настольное приложение MSVC+Qt 47/47 и
Python 24/24.

После A6 чистый раскрой сохраняет 44 CTest-проверки. Полный режим без
графического интерфейса содержит 48 проверок, настольный режим — 49. Отдельные
`AIPackaging_ApplicationTests` работают только с имитациями портов, а
`AIPackaging_DesktopInfrastructureTests` проверяют JSON, точный валидатор,
фоновое выполнение и отмену.

M6.3/A7 сохраняет 44 проверки чистого раскроя и 48 проверок режима без
графического интерфейса, где ONNX отключён. Настольная конфигурация с
`BUILD_ONNX_BACKEND=ON` содержит 54 записи CTest: отдельные тесты получения
вывода и четыре сценария CLI добавлены к прежним 49. Синтетический комплект не
содержит обученных весов и проверяет динамические оси, SHA-256, стабильность,
отмену и обязательную точную проверку решения.

После A8 настольные тесты проверяют единственное `PolygonMainWindow`, отсутствие
клеточной вкладки, доступность файловых действий во время поиска, модель,
отмену, частичный результат и сохранение проверенного решения. Отдельный тест
отклоняет `aipackaging.packing_scene` с явной диагностикой. Чистая настольная
конфигурация не создаёт цели `AIPackaging_Math`, `AIPackaging_Domain`,
`AIPackaging_Contract` и `AIPackaging_App`; режим без графического интерфейса
запускает прикладные тесты через `BUILD_APPLICATION_TESTS=ON`. Клеточные и
полигональные эталоны CLI и замороженные наборы данных остаются неизменными.
Итоговый локальный прогон A8: 44/44 проверки чистого раскроя, 46/46 полного
режима без графического интерфейса, 52/52 настольного режима с ONNX и 10/10
настольного режима без ONNX. Полный Python-набор проходит 61/61 проверку.

После A5 Python набор тестов дополнительно проверяет общие канонический JSON/JSONL кодеки,
gzip с `mtime=0`, SHA-256, безопасные пути к частям набора данных, атомарную
оболочку кэша,
совместимость импортов и команд обработки данных без загрузки модели, для
которых запрещён импорт PyTorch. Клеточный и
полигональный минимальные наборы данных до/после декомпозиции совпадают побайтово при одной
сборка ревизия кода; варианты с одним и двумя рабочий процесс также идентичны. После `M6.1R`
полный pytest содержит 43 успешно пройденных теста, включая схема, семейство,
возобновление, повторное проигрывание и регрессионные проверки сравнительного испытания.

`747ADE28A858DE2F1D484CDF6C942DF07CB59AF017EEB886F8C18D9105422C44`.

Средство проверки архитектуры Python использует полные пути модулей и правило
самого длинного префикса
владение. Отрицательные самопроверки отдельно запрещают набор данных → PyTorch и
«общий модуль наборов данных → обучение».

Рабочий процесс `quality.yml` запускает чистый раскрой в Linux, Windows MSVC
без графического интерфейса и Python 3.13. После R3 отдельные задания проверяют
настольную сборку Windows с Qt 6.9.3 при включённом и выключенном ONNX, а также
чистый раскрой Linux с `AddressSanitizer` и `UndefinedBehaviorSanitizer`.
Для тестов виджетов копируется модуль Qt `QOffscreenIntegrationPlugin`, поэтому
проверка не требует открытого экрана. Эти задания не считаются пройденными до
публикации изменений и фактического запуска GitHub Actions.

R3 дополнительно проверяет отказ записи и замены файла решения, повторный запуск
из итогового события фоновой работы, откат полигональной обучаемой среды при
исключении и точное продолжение BC с границы завершённой эпохи. Проверка
контрольной точки старого формата для оценки сохраняется, но продолжение BC без
подтверждённой границы эпохи отклоняется. Эти проверки не запускают обучение
канонической модели и не изменяют замороженный набор данных.

На этапе A2 команда `nesting` использовала отдельную предустановку и доказывала отсутствие Qt,
цели сборки `Math` и унаследованного контура. Тогда чистый раскрой выполнял 39 проверок CTest,
полный контур без графического интерфейса — 41, настольное приложение — 42.
После CTest средство запуска сравнивает 20 клеточных и полигональных решений CLI с
семантическими SHA-256 A1: учитываются статус, размещения, целевая функция и
детерминированные счётчики, но исключаются фактическое время, ревизия кода и изменяемая
версия проекта.
Для клеточный случайный зафиксированы отдельные A1-хеши MinGW и MSVC, поскольку
стандартный `shuffle` этих библиотек даёт разные, но повторяемые перестановки.
