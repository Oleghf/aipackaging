# Архитектура AIPackaging

## Принципы

- Геометрия и поиск не зависят от Qt или Python.
- Пользовательский интерфейс не получает внутренние типы решателя.
- Нейросеть выбирает только действие из каталога, созданного геометрическим
  ядром.
- Любое публикуемое решение повторно проверяется независимым валидатором.
- Форматы обмена и каталоги действий версионируются отдельно от кода.
- Фоновые адаптеры доставляют события в поток владельца через прикладной
  диспетчер.

## Цели сборки

```text
AIPackaging_NestingCore
  ├─ AIPackaging_SearchContracts
  ├─ AIPackaging_GridCore
  └─ AIPackaging_PolygonCore ──private──> Clipper2

AIPackaging_Search
  └─ SearchContracts + GridCore + PolygonCore

AIPackaging_Json
  └─ SearchContracts + GridCore + PolygonCore
     └─ private: nlohmann/json

AIPackaging_Learning
  └─ GridCore + PolygonCore

AIPackaging_OnnxInference
  └─ Learning + Search + ONNX Runtime

AIPackaging_Application
  └─ нейтральные прикладные контракты

AIPackaging_DesktopInfrastructure
  └─ Application + Search + Json + PolygonCore
     └─ optional: OnnxInference

AIPackaging_GUI
  └─ Application + Qt Widgets
```

`AIPackaging_SolverImpl` и `AIPackaging_Solver` остаются совместимыми
интерфейсными целями исследовательского API. Чистая сборка ядра не создаёт
прикладной слой, инфраструктуру или GUI.

`AIPackaging_DesktopInfrastructure` остаётся одной целью сборки, но её
реализация разделена по обязанностям:

- `PolygonArtifactStore` хранит неизменяемые задачи, решения и модели;
- `LocalPolygonDocumentGateway` загружает и атомарно сохраняет документы;
- шлюз и средство фоновой загрузки модели проверяют комплект ONNX;
- базовая, ONNX- и маршрутизирующая внутренние реализации выполняют раскрой;
- `StdThreadNestingJobRunner` управляет потоком, отменой и уведомлениями;
- закрытый преобразователь строит прикладные сцены из доменных результатов.

Безопасная доставка событий и RAII-охрана непереданных идентификаторов общие
для фоновой загрузки модели и раскроя. Совместимый заголовок
`polygondesktopinfrastructure.h` только собирает однозначные заголовки
компонентов и не владеет реализацией.

`PolygonWorkspaceWidget` остаётся совместимым фасадом Qt и собирает четыре
закрытые детали представления:

- `PolygonDocumentPanel` показывает задачу, дерево деталей, легенду и выбор;
- `PolygonRunPanel` формирует прикладной запрос запуска и управляет моделью;
- `PolygonStatusPanel` показывает сообщение, ход выполнения и метрики;
- `PolygonCanvasWidget` рисует лист, остаток, отступ и размещения отдельными
  операциями без вычисления доменной геометрии.

`PolygonMainWindow` владеет файловыми диалогами, недавними файлами и
`QSettings`, но передаёт запуск и публикацию состояния через прежний
прикладной контракт. Панели не образуют новые цели сборки и не зависят от
решателя или ONNX.

## Владение данными

- `GridProblem` и связанные типы принадлежат клеточному ядру.
- `PolygonProblem`, нормализованная геометрия, состояние размещения и точный
  валидатор принадлежат полигональному ядру.
- `SolverConfig`, ход выполнения, отмена и общие метаданные принадлежат
  контрактам поиска.
- Разбор и запись JSON принадлежат `AIPackaging_Json`; типы JSON не входят в
  публичные заголовки ядра.
- Наблюдения и переходы обучаемых сред принадлежат `AIPackaging_Learning`.
- Прикладные идентификаторы документов, моделей и решений принадлежат
  `AIPackaging_Application` и не раскрывают объекты решателя.
- Неизменяемые задачи, решения и модели хранятся в инфраструктурных хранилищах
  и выдаются прикладному слою как непрозрачные идентификаторы.
- Qt владеет только виджетами, настройками окна и структурами представления.

## Открытие и отображение задачи

```text
PolygonMainWindow
  -> IPolygonDocumentGateway
  -> строгий разбор polygon_problem v1
  -> нормализация PolygonProblem
  -> PolygonArtifactStore
  -> PolygonWorkspaceController
  -> PolygonWorkspaceSnapshot
  -> PolygonWorkspaceWidget
```

Ошибка нового файла не уничтожает предыдущий корректный документ или решение.
`ActivePolygonDocument` хранит источник, признаки `dirty`, `valid`, `running` и
устаревание решения, но не зависит от Qt, JSON, файловой системы или поиска.

## Выполнение раскроя

```text
NestingRunRequest
  -> StdThreadNestingJobRunner
  -> IPolygonNestingBackend
       ├─ BaselinePolygonBackend
       └─ OnnxPolygonBackend
  -> PolygonEnvironment
  -> PolygonSolutionValidator
  -> PolygonWorkspaceController
  -> проверенная сцена и необязательный PolygonSolutionHandle
```

Контроллер является однопоточным автоматом состояния. Средство запуска владеет
`std::jthread`, отменой и ограничением частоты уведомлений. Каждое событие
содержит идентификатор запуска; запоздалые события старой работы игнорируются.
Отменённый результат можно показать, но нельзя сохранить.

Общий механизм поиска реализует последовательный, случайный и лучевой жизненные
циклы. Клеточный и полигональный адаптеры предоставляют представление состояния,
кандидатов, ранжирование и построение решения. Геометрия и целевые функции между
ними не унифицируются.

## Загрузка и применение модели

Проверка модели выполняется отдельной фоновой работой:

```text
PolygonMainWindow
  -> IPolygonModelJobRunner
  -> IPolygonModelGateway
  -> проверка metadata.json и SHA-256
  -> создание последовательных сеансов ONNX Runtime CPU
  -> PolygonModelHandle
```

Новая модель публикуется только после полной проверки. Отмена, ошибка или
запоздалое событие сохраняют прежнюю рабочую модель. Без модели базовые режимы
доступны, а нейросетевые заблокированы.

Политика не передаёт произвольные координаты. Она выбирает экземпляр, поворот и
позицию из текущего динамического каталога `PolygonLearningEnvironment`.
Гибридный режим сравнивает нейросетевой результат с
`random-left-bottom/64` общим C++-компаратором. После ошибки модели он может
вернуть явно помеченный проверенный результат резервного алгоритма.

## Геометрия и каталог действий

Входные миллиметры переводятся в микроны типа `int64`. Кривые
детерминированно аппроксимируются, кольца нормализуются, а самопересечения и
некорректные отверстия отклоняются. Модель столкновений использует заполненное
внешнее кольцо, поэтому вложение в отверстия пока запрещено.

Для каждой ориентации среда строит область допустимого переноса и вычитает NFP
уже размещённых деталей. Кандидаты проходят точный `canApply` и получают
стабильный порядок. Версия каталога 1 сохранена для набора M6.1 и комплекта
модели; версия 2 исправляет пересечения границ NFP и используется обычными
базовыми запусками.

`sheetMargin` и `partSpacing` влияют на допустимость независимо. `kerf` пока
является метаданными будущей траектории реза.

## Форматы обмена

Действующие публичные форматы:

- `aipackaging.grid_problem` v1;
- `aipackaging.grid_solution` v1/v2;
- `aipackaging.polygon_problem` v1;
- `aipackaging.polygon_solution` v1/v2;
- `aipackaging.polygon_dataset` v1/v2;
- `aipackaging.polygon_trajectory` v1;
- `aipackaging.polygon_policy` v1/v2;
- контракты конфигурации, запуска и отчёта обучения версии 1.

Неизвестные поля и неподдерживаемые версии отклоняются. Схемы находятся в
`schemas/`, а общий набор контрактных примеров проверяется C++ и Python.

## Границы M7–M8

Будущее редактирование использует следующие направления зависимостей:

```text
GUI -> Application -> Editor commands
DxfImport -> Editor model
DesktopInfrastructure -> Application + Search + Json + OnnxInference
```

`Editor` не зависит от Qt, JSON, DXF, поиска или ONNX. Адаптер DXF зависит
только от нейтральной редактируемой модели; его внутренние типы не выходят в
прикладные порты. Решатель получает неизменяемый снимок только полностью
проверенного документа.

Фоновый импорт DXF получит собственные шлюз и средство запуска. Он может
переиспользовать невыбрасывающую доставку событий, но не расширяет классы
поиска, ONNX или фонового выполнения раскроя.

## Обязательные инварианты

- Детали не пересекаются и не выходят за полезную область листа.
- Генератор кандидатов и независимый валидатор одинаково трактуют производственные
  расстояния.
- Временные метрики не участвуют в выборе лучшего решения.
- Одинаковые вход, версия каталога, настройки и начальное значение дают
  одинаковый детерминированный результат.
- Ошибка загрузки, поиска или модели не уничтожает последний корректный объект.
- Замена документа или закрытие приложения сначала отменяет и завершает
  активную фоновую работу.
