# ADR-0009: модульная полигональная платформа и вывод унаследованного настольного контура

- Статус: принято и реализовано этапами A1–A8
- Дата: 2026-09-11

## Контекст

После M5 в проекте сосуществуют два контура настольного приложения и домена, а
также одна крупная цель сборки решателя. Полигональная среда уже является
основой базовых алгоритмов, API обучения, набора данных Python и новой вкладки
Qt, но ввод-вывод, поиск, геометрия и ML находятся в одной библиотеке. Общие
статусы и метаданные формально принадлежат клеточным контрактам.

M6.2 заморозит полигональную обучаемую политику, а M6.3 добавит вторую внутреннюю
реализацию настольного приложения. Если начать их поверх текущих границ,
временные зависимости C++ станут частью контрактов развёртывания модели.

## Решение

Развивать проект как модульный монолит с полигональным ядром. Выделить общие
контракты, `NestingCore`, поиск, обучение, JSON и порты прикладного слоя.
Конкретные базовые алгоритмы, файловая система, многопоточность, Qt, pybind11 и
механизм выполнения ONNX являются адаптерами.

Сохранить форматы обмена и старые точки входа C++ через перенаправляющие заголовки и
цель сборки совместимости. Не вводить универсальную иерархию механизмов выполнения геометрии:
клеточный и полигональный контуры могут использовать общий механизм выполнения
поиска, но сохраняют собственные адаптеры состояния и кандидатов.

Клеточный решатель остаётся исследовательским компонентом совместимости для
воспроизводимости M1-M3. Клеточное настольное приложение `Board/Figure`
изолируется признаком сборки и выводится после
полигонального функционального паритета. Его внутреннюю событийную архитектуру не
переписывать перед удалением.

Архитектурные этапы A1-A5 выполняются до M6.2. Порты прикладного слоя и вынос
средства запуска выполнения завершаются до M6.3. Любая нейросетевая или
гибридная внутренняя реализация обязана выбирать действия среды C++ и проходить
тот же точный валидатор.

Первый шаг решения реализуется в A2 без изменения пространство имён и форматы обмена:

- `AIPackaging_NestingCore` владеет общими контрактами и строковыми
  преобразованиями статуса и семейства;
- `AIPackaging_SolverImpl` временно владеет восемью существующими клеточными и
  полигональными единицами трансляции и публично зависит только от ядра;
- `AIPackaging_Solver` становится целью `INTERFACE` для совместимости со старыми
  плоскими заголовками, прикладным слоем и GUI;
- `SolverKind` и `SolverConfig` принадлежат отдельным контрактам поиска, но общее
  управление выполнением откладывается до A4;
- цели сборки унаследованного контура создаются только для настольного приложения либо при явном
  `BUILD_LEGACY_TESTS=ON`.

## Рассмотренные варианты

### Сохранить единый `AIPackaging_Solver`

Отклонено: минимальная стоимость сейчас приводит к связанным изменениям
геометрии, набора данных, привязок Python/C++ и развёртывания на каждом
следующем этапе.

### Полностью переписать проект вокруг новой модели

Отклонено: рабочие алгоритмы и 38/38 + 31/31 тестов уже дают безопасную базу для
извлечения модулей. Полная перепись создаст непроверяемое изменение геометрии.

### Сделать отдельные сервисы для решателя и обучения

Отклонено: для одного разработчика межпроцессное взаимодействие, развёртывание
и схема координации не дают
компенсирующей пользы. Нужны на этапе компиляции границы, а не распределённая система.

## Последствия

Положительные:

- M6.2 обучается поверх стабильных контрактов обучения и ядра;
- M6.3 добавляет внутреннюю реализацию ONNX без изменений представления Qt;
- сборки без графического интерфейса и для Python не зависят от унаследованного настольного контура;
- формат обмена совместимость контролируется отдельно от внутренней структуры;
- унаследованный контур можно удалить без потери клеточных исследовательских артефактов.

Отрицательные:

- перед обучением появляется отдельный архитектурный этап;
- временно поддерживаются перенаправляющие заголовки и цель сборки совместимости;
- целей сборки CMake и тестовых исполняемых файлов станет больше;
- побайтовый и геометрический функциональный паритет нужно проверять после каждого перемещения.

Риски ограничиваются малыми этапами, признаками сборки и запретом совмещать
перемещение исходного кода с изменением алгоритма.
